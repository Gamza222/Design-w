# ДизайнСейчас

Мультиязычный имиджевый сайт студии дизайна интерьера: услуги, портфолио, блог. Быстрый,
SEO-friendly, статический (SSG), контент пополняется через MDX.

## Стек

Vite · React 19 · TypeScript (strict) · React Router v7 (framework mode, `ssr:false` + prerender →
статика) · react-i18next (RU + EN) · MDX · SCSS Modules + CSS-переменные · GSAP/ScrollSmoother ·
Vitest + Playwright · ESLint/Steiger/Stylelint/Prettier · деплой на REG.RU.

Архитектура — [Feature-Sliced Design](https://feature-sliced.design): `src/{app,pages,widgets,features,entities,shared}`.

## Команды

```bash
npm install          # установка зависимостей
npm run dev          # дев-сервер (http://localhost:5173)
npm run build        # сборка + prerender в build/client
npm run preview      # отдать собранную статику (http://localhost:3000)

npm run typecheck    # react-router typegen + tsc
npm run lint         # ESLint + Stylelint
npm run lint:fsd     # Steiger (границы FSD)
npm test             # Vitest
npm run e2e          # Playwright: Chromium + WebKit (поднимает build + preview сам)
php tests/backend/lead-test.php # изолированные тесты доставки, PHP 7.4+
node --test tests/backend/http-test.mjs # HTTP-ошибки PHP без реальных сообщений
node --test scripts/generate-lead-config.test.mjs # проверка deploy-конфига
node scripts/setup-leads.mjs --self-test # проверка мастера настройки без сети и секретов
```

## Контент

- Блог: `content/blog/{ru,en}/<slug>.mdx`
- Портфолио: `content/portfolio/{ru,en}/<slug>.mdx`

После добавления MDX нужен `npm run build` (статическая сборка, без on-demand).

Фотографии — только реальные проекты студии. Веб-версии WebP создаются из сохранённых JPEG
без изменения кадра и разрешения: `node scripts/optimize-real-images.mjs` (нужен `cwebp`).
JPEG также сохраняются для социальных превью. HTML, CSS и JavaScript сжимаются на хостинге
через `mod_deflate`; локальный preview использует такое же gzip-сжатие.

## Деплой

Production — статический хостинг REG.RU, корень сайта `/www/designseichas.ru`. Workflow `CI`
после успешных проверок собирает проект и синхронизирует содержимое `build/client/` по FTPS при
push в `main`.

### Доставка заявок

Формы отправляют заявку на `POST /api/lead.php`. Обработчик разворачивается вместе со статикой на
том же сервере REG.RU с PHP 7.4+ и исходящим доступом к Telegram API (HTTPS). Заявки отправляются
только двум выбранным личным Telegram-аккаунтам, отправившим `/start` боту; почта и пароль
Яндекса не нужны. Имена аккаунтов не закреплены в коде: доставка использует два сохранённых
числовых chat ID. Новые пользователи, отправившие `/start` после настройки, автоматически
получателями заявок не становятся.

На сервере не нужен отдельный постоянно работающий процесс бота: PHP вызывает `sendMessage`
при отправке формы. Polling и webhook для этого не требуются. Локальный мастер настройки нужен
однократно для подключения двух получателей, а не для работы сайта. После публикации терминал
можно закрыть. Успех формы показывается только после подтверждения Telegram для обоих сообщений;
это не означает, что адресаты уже прочитали сообщения.

Сервер выдаёт публичный номер из 9 читаемых букв/цифр; API возвращает его в `leadNumber` и
`requestId`, оба Telegram-сообщения содержат тот же номер. Длинный `submissionId` остаётся
внутренним ключом идемпотентности. Повтор неизменённой заявки досылает только неподтверждённые
отправления; изменённые данные с прежним ключом отклоняются с 409. Контекст калькулятора,
выбранная услуга/кейс и разрешённые UTM передаются обоим получателям.

История номеров и доставок хранится без контактного текста в закрытом `.designseichas-leads`
рядом с физическим корнем сайта, вне `build/client` и области FTPS mirror. Путь вычисляет PHP,
поэтому `DEPLOY_PATH=.` в FTP chroot его не меняет. Записи заменяются атомарно, резервирование
номера проверяет совпадения между PHP-процессами. Каталог нельзя очищать вместе с временными
файлами. Для VPS можно задать абсолютный `LEAD_STATE_DIR` (environment либо GitHub variable);
web root и временные папки запрещены. Гарантии «ровно одна доставка» при обрыве после принятия
сообщения Telegram нет: номер позволяет распознать такой повтор.

`GET /api/lead.php?health=1` проверяет PHP, приватное атомарное хранилище и конфигурацию двух
адресатов без Telegram-запросов; workflow проверяет его после загрузки. Инструкции по переносу
прежней временной истории, резервному копированию и VPS: [backend](docs/finaltask-backend.md).

Перед production-деплоем добавьте в GitHub Actions три repository secret
([настройки репозитория](https://github.com/Gamza222/Design-w/settings/secrets/actions)):

- `LEAD_TELEGRAM_BOT_TOKEN` — токен бота от BotFather;
- `LEAD_TELEGRAM_CHAT_ID` — числовой ID первого выбранного личного чата с этим ботом;
- `LEAD_TELEGRAM_CHAT_ID_ADDITIONAL` — числовой ID второго выбранного личного чата с этим ботом.

Оба пользователя должны открыть созданного бота и нажать «Запустить» (`/start`). После этого ID
можно получить из `message.chat.id` в ответе метода `getUpdates` этого бота. Имена личных аккаунтов
`@…` не заменяют chat ID. Два ID должны быть разными. Не отправляйте токен в чат или Git:
добавляйте его напрямую в GitHub Secrets. Инструкции:
[Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

Для подключения двух личных аккаунтов есть локальный мастер настройки. В обычном терминале
из папки проекта выполните:

```bash
node scripts/setup-leads.mjs
```

Нужны Node.js 22+ и GitHub CLI (`gh`) с доступом к настройкам репозитория. Если вход ещё не
выполнен, мастер предложит `gh auth login --hostname github.com`. Введите токен созданного бота
из BotFather по запросу мастера; ввод скрыт звёздочками. Мастер покажет имя именно этого бота,
найдёт личные аккаунты, отправившие `/start`, и покажет их имена (если заданы) и числовые ID.
Если найдено ровно два аккаунта, мастер использует их; если больше двух, нужно вручную выбрать
два ID — первые попавшиеся чаты автоматически не подключаются. Если аккаунтов пока меньше двух,
мастер предложит отправить свежий `/start`. После проверки обоих ID через `getChat` мастер
сохранит три секрета именно в `Gamza222/Design-w`. При необходимости существующие значения
будут заменены. Он читает `getUpdates` без `offset`, не удаляет сообщения из очереди и не меняет
webhook. Секреты передаются GitHub CLI через stdin, не записываются в локальные файлы и не
появляются в аргументах команд или выводе. При ошибке сохранения повторите настройку целиком.
По отдельному подтверждению мастер может отправить по одному помеченному тестовому сообщению
каждому получателю. Команда не запускает деплой; проверка самой формы выполняется после публикации.

Если прежний мастер зациклился на Enter, завершите его `Ctrl+C` и запустите команду заново после
обновления файлов. Новый мастер не ищет заранее заданные имена пользователей и показывает
обнаруженные личные аккаунты с их ID.
Проверьте, что оба аккаунта отправляют `/start` именно боту, чьё имя показано в терминале, и делают
это после запроса мастера: Telegram не хранит обновления дольше 24 часов. При подключённом webhook
или другом процессе, забирающем обновления, автоматический поиск может быть недоступен. Мастер
сообщит об этом; используйте предложенный ручной ввод числовых ID (`id`). Он проверит, что это
два разных доступных боту личных чата, и выведет подтверждённые аккаунты. При ручном вводе
получателей выбираете вы: внимательно сверяйте вводимые ID. Webhook автоматически не удаляется.

Во время deploy workflow создаёт `build/client/api/.lead-config.php`; файл игнорируется Git и
закрыт от HTTP-доступа правилами `public/api/.htaccess`. Без всех трёх значений deploy намеренно
останавливается, чтобы не публиковать форму, которая теряет заявки.

До загрузки файлов workflow также проверяет токен через `getMe` и доступ бота к обоим чатам через
`getChat` в `scripts/check-lead-delivery.php`, без отправки сообщений и чтения входящих обновлений.
После загрузки workflow отдельно проверяет работоспособность хранилища в PHP на хостинге.

После публикации отправьте тестовую заявку с сайта и подтвердите её получение в обоих чатах.
Автоматические тесты не отправляют настоящие сообщения.

Перед первым деплоем в GitHub необходимо добавить secret `DEPLOY_FTP_PASSWORD`, variables
`DEPLOY_USER`, `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_PATH`, `DEPLOY_FTP_CERT_SHA1`, затем включить
`DEPLOY_ENABLED=true`. Соединение требует FTP с явным TLS; `.well-known` сохраняется при
синхронизации для продления SSL-сертификата. Самоподписанный серверный сертификат принимается
только при совпадении закреплённого отпечатка.
