# Поиск, региональность и измерение заявок

Актуально для релиза от 23 октября 2026 года. Основная локация — Москва: владелец подтвердил офис и команду. Дистанционная работа по России и Беларуси сохранена. Санкт-Петербург не выделяется отдельной посадочной страницей или офисом.

## Что настроено на сайте

- Существующие главная, каталог услуг, контакты, описание студии и три страницы услуг получили конкретизацию по Москве и составу услуг на RU/EN/BE.
- Canonical, hreflang и Sitemap содержат реальные конечные URL. В Sitemap остаётся 66 страниц, по 22 на язык. Новых страниц-заготовок нет.
- Организация имеет единый ID `https://designseichas.ru/#organization`, типы Organization/LocalBusiness, реальный опубликованный московский адрес, координаты и контакты. На услугах — Service и BreadcrumbList. Новых филиалов, отзывов и рейтингов не добавляли.
- После подтверждения доставки заявки сервером отправляются GA4 `generate_lead` и цель Метрики `lead_success`. Параметр `lead_type` принимает только `project` или `consultation`. Имя, телефон, комментарий, номер заявки и расчётная стоимость в эти события не передаются.
- Ошибка запроса или ответ без корректного подтверждения не создаёт конверсию. Повтор одного `submissionId` подавляется в текущей вкладке. Недоступная аналитика не мешает подтверждению успешной заявки.

## Google Search Console — действия владельца

1. Открыть ресурс для `https://designseichas.ru/`. Если доступ ещё не подтверждён, использовать подходящий способ подтверждения; DNS в этой задаче не менялся.
2. Отправить `https://designseichas.ru/sitemap.xml` в разделе Sitemap. Не создавать дополнительные карты ради количества URL.
3. Проверить URL главной, `/services/`, `/contact/`, `/planirovka-kvartiry/`, `/3d-vizualizaciya-interera/`, `/eskiznyj-dizajn-proekt/`. Проверить выбранный Google canonical и запросить индексирование изменённых страниц.
4. Проверить отчёты об индексировании, ручных мерах и безопасности. Техническая доступность страницы не означает, что поисковик уже её включил в индекс.
5. В отчёте эффективности отдельно смотреть запросы бренда «дизайн сейчас» / «студия дизайна дизайн сейчас», услуг и услуг с Москвой; сравнивать показы, клики и страницы входа. Вывод о причинах слабых позиций требует этих данных, а не только осмотра HTML.
6. В отчёте Core Web Vitals смотреть реальные пользовательские данные. Отсутствие достаточной выборки не означает автоматически хороший INP.

Google сообщает, что повторный обход может занять дни или недели и не гарантирует включение в результаты: [запрос повторного обхода](https://developers.google.com/search/docs/crawling-indexing/ask-google-to-recrawl).

## Яндекс Вебмастер и Бизнес — действия владельца

1. Проверить основное зеркало `https://designseichas.ru/`, Sitemap и состояние индексирования.
2. Отправить изменённые ключевые страницы на переобход.
3. В региональности проверить, какой регион назначен сейчас. Московский офис должен быть подтверждён страницей `/contact/` и карточкой реальной организации. Если сайт в целом обслуживает Россию, регион «Россия» тоже допустим; не менять его вслепую только ради одного запроса.
4. Создать или актуализировать карточку реального московского офиса в Яндекс Бизнесе: название, опубликованный адрес, телефон и основной URL должны совпадать. Не создавать фиктивную карточку Санкт-Петербурга или других городов.
5. Проверить выбранный регион после модерации. Региональность — один из факторов, а не запрет показа сайта в остальных городах: [официальная инструкция Яндекса](https://yandex.ru/support/webmaster/ru/site-geography/site-region).

## Настройка конверсий и рекламы — действия владельца

1. В Метрике счётчика `113598335` создать цель типа «Целевое событие»/JavaScript-событие с точным идентификатором `lead_success`. Название, например, «Заявка подтверждена сервером». Для вызова `reachGoal` идентификатор должен соответствовать цели: [документация Метрики](https://yandex.ru/support/metrica/ru/objects/reachgoal).
2. В GA4 для потока `G-FGETKE5FZQ` отметить `generate_lead` как ключевое событие. Событие соответствует рекомендованному типу Google: [generate_lead](https://developers.google.com/analytics/devguides/collection/ga4/reference/events#generate_lead).
3. Связать нужный счётчик/поток с рекламным аккаунтом и выбрать подтверждённую заявку как целевое действие. Автоматический `form_submit`, нажатие кнопки и открытие формы не означают успешную доставку заявки.
4. Проверить настройки местоположения рекламной кампании: Москва — отдельный понятный сегмент; другие регионы для онлайн-услуг — по реальным условиям бизнеса. Изменение SEO-текста не меняет геотаргетинг объявлений.
5. Проверить соответствие объявления странице входа: планировка → `/planirovka-kvartiry/`, 3D → `/3d-vizualizaciya-interera/`, полный проект → `/eskiznyj-dizajn-proekt/`, сравнение пакетов → `/services/` или калькулятор на главной. Использовать конечные HTTPS-URL со слешем и UTM-метками.
6. Анализировать реальные поисковые фразы, стоимость подтверждённой заявки и её качество. Без доступа к кампании нельзя подтвердить, что бюджет расходуется на нужную аудиторию, или подобрать проверенный список минус-фраз.

Во время технических тестов заявки перехватываются локально: владельцу и команде не отправляются тестовые сообщения. Настройки рекламных аккаунтов, Search Console, Вебмастера и Бизнеса этим релизом не изменяются.

## Ограничения и дальнейшие работы

- Причина слабых позиций не доказана: нет данных поисковых кабинетов о спросе, показах, выбранных canonical и индексации. Нельзя обещать первые позиции или немедленный рост после публикации.
- Структура недостающих услуг подготовлена в [плане страниц](service-page-plan.md). Чертежи, коллажи, общая страница дизайн-проекта квартиры и отдельная страница стоимости требуют согласованных материалов; пока доступны существующие пакеты, калькулятор и каталог.
- На REG.RU внешний nginx сначала переводит HTTP на HTTPS, иногда с явным `:443`. Для HTTP+www остаётся дополнительный переход к основному домену. Это настройка хостинга; окончательный HTTPS canonical корректен.
- Nginx кеширует `/metrika.js` на 45 дней, игнорируя Apache `no-cache` для этого файла. Текущий счётчик работает; при следующем изменении загрузчика нужен новый URL версии либо настройка nginx в панели. Бандлы текущих изменений имеют новые хеши.
- Полевые CWV/INP не удалось получить через PageSpeed API: сервис вернул 429 (quota=0). Лабораторные замеры не подменяют данные реальных посетителей.
- Реквизиты юридического лица в исходном каталоге не заполнены; они не выдумывались и не подменялись демонстрационными данными. Владельцу нужно передать реальные сведения для отдельного обновления соответствующей страницы.

## Производительность

До изменений live Lighthouse с заблокированными сторонними счётчиками: mobile85/100, LCP3,93с, CLS0, TBT75мс; desktop97/100, LCP1,13с, CLS0,0039, TBT0мс. Это лабораторные прогоны, зависящие от сети и нагрузки, без веса аналитики.

Cookie-уведомление раньше добавлялось только после загрузки и гидрации JavaScript и становилось поздним LCP-элементом. Теперь оно есть в первоначальном HTML; для уже ознакомившихся посетителей скрывается до первого отображения. Сценарии нового посетителя, сохранённого подтверждения, заблокированного хранилища и отключённого JavaScript проверены в Chromium и WebKit.

В изолированном сравнении одинаковых локальных сборок с реальным DevTools throttling LCP снизился5,53→3,15с, CLS0→0,020 (остаётся ниже0,1); TBT241→248мс. В моделируемом режиме Lighthouse изменение LCP небольшое4,82→4,76с, поэтому эти числа не являются обещанием скорости для каждого посетителя. Качество фото не менялось: сохранены responsive WebP, размеры, приоритет первого изображения и lazy loading вне первого экрана. [О различиях лабораторных и полевых показателей](https://web.dev/articles/lab-and-field-data-differences).
