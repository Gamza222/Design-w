## Обычный откат через новый коммит

1. Выполнить `git fetch origin`, создать отдельную ветку от актуального `origin/main` и проверить `git log --oneline 9d040d1..origin/main`.
2. Выбрать коммит или коммиты именно SEO-релиза и отменить их командой `git revert`, начиная с последнего. Для merge-коммита сначала проверить родителей и использовать `git revert -m 1` только если первый родитель — прежняя `main`. Не отменять попутно последующие независимые изменения.
3. Проверить diff: должны сохраниться ранее работающие GA, Метрика, PHP API и конфигурация FTPS. Если после `9d040d1` были только изменения этого SEO-релиза, итоговое дерево должно совпадать с `9d040d1`; проверить `git diff 9d040d1 -- .`.
4. Выполнить проверки проекта: `npm run typecheck`, `npm run lint`, `npm run lint:fsd`, `npm test`, `npm run build` и `npm run e2e`. Изменения `.htaccess` дополнительно проверить реальным Apache и запросами из следующего раздела.
5. Опубликовать revert-коммит в `main` обычным PR/merge. Workflow `.github/workflows/ci.yml` после успешных quality и e2e соберёт проект и загрузит `build/client/` на REG.RU через FTPS. Не переписывать историю `main`, не использовать force push и не подменять откат ручной заливкой локальной сборки.
6. Дождаться успешного job `Deploy to REG.RU over FTPS`, затем проверить публичные URL и health. Успех отдельного Vercel deployment не подтверждает публикацию на REG.RU.

Workflow использует GitHub Secrets, пересоздаёт закрытый `api/.lead-config.php`, проверяет доступ к двум Telegram-получателям без сообщений и проверяет health после загрузки. Архив исходников не содержит этот секретный runtime-конфиг и не должен напрямую заменять содержимое хостинга.

`mirror --reverse --delete` не является атомарным переключением релиза. Не запускать одновременно несколько deploy или ручное копирование файлов. Каталог `.designseichas-leads` с историей заявок находится вне web root и исключён из зеркала вместе с `.well-known`; не удалять, не восстанавливать из устаревшей копии и не менять его при откате фронтенда. Процедура восстановления состояния заявок описана отдельно в [документации backend](../finaltask-backend.md).

## Проверка после публикации

Проверять Location без автоматического следования редиректу и с сохранением повторных слешей (`curl --path-as-is -I`). Затем отдельно проверить конечный URL и отсутствие циклов.

- `https://designseichas.ru/` и `/about/` — `200`, правильный canonical, GA и Метрика присутствуют.
- `https://www.designseichas.ru/about/`, `/about`, `/about/index.html` — `301` на соответствующий основной URL с завершающим `/`.
- `https://designseichas.ru//about/` и `/about//` — после SEO-релиза `301` на `/about/`. В исходной версии `9d040d1` эти варианты возвращали `200` с правильным canonical: это ожидаемое возвращение старого поведения при полном откате.
- `/about//?utm_source=https://ads.example/a//b&x=1` — query должен сохраниться побайтно; обычный `/about/?utm_source=https://ads.example/a//b&x=1` не должен запускать нормализацию слешей.
- `/__spa-fallback.html` — `200`, после SEO-релиза заголовок `X-Robots-Tag: noindex`; `/` и `/about/` не должны получить этот заголовок. Служебный файл не удалять: он относится к сборке React Router.
- `/robots.txt` и `/sitemap.xml` — `200`; неизвестный URL — `404`, а не пустая страница с `200`.
- `/api/lead.php?health=1` — `200`, `ok: true`, `storage: ready`, `recipients: 2`. Проверять только GET health, не отправлять реальную тестовую заявку автоматически.

23 октября правила слешей и заголовок для SPA fallback проверены на локальном Apache 2.4.62: синтаксис корректен, 14 направленных проверок прошли. Проверены query/UTM с `//`, экранированные `%20`, `%3F`, `%23`, отсутствие циклов и отсутствие `noindex` у обычных страниц. Результат сохранён в `/tmp/design-w-seo-apache-check.json`. Несколько отдельных групп повторных слешей устраняются последовательными конечными редиректами; обычные двойные слеши исправляются за один переход. Публичную работу всё равно нужно подтвердить: перед Apache находится nginx.

## Что зависит от REG.RU

На дату аудита `.htaccess` применяется к HTML, robots.txt и sitemap.xml: работают редиректы `www`, `index.html`, завершающий слеш и заголовки HTML. Запросы JS/CSS обслуживаются nginx напрямую: `/metrika.js` получает `Cache-Control: max-age=3888000`, несмотря на `no-cache` в `.htaccess`. Изменение URL ресурса при обновлении исправляет устаревший браузерный кеш на уровне кода; изменение срока кеша требует настройки nginx.

Первый HTTP → HTTPS редирект также выполняет nginx и добавляет `:443`. Для `http://www.designseichas.ru/` остаются два перехода: сначала HTTPS www, затем HTTPS без www. Убрать этот первый лишний переход одной правкой `.htaccess` нельзя. Нужны настройки домена/редиректа в панели REG.RU либо конфигурация nginx с сохранением пути и query. DNS менять для этого не нужно.

Панель `https://server173.hosting.reg.ru:1500/` и SSH-порт доступны по сети. Локально имеется ключ с именем `designseichas_github_actions`, а в GitHub — secret `DEPLOY_SSH_KEY`; пригодность этих учётных данных для панели/SSH в этом аудите не проверялась. Подтверждённый рабочий способ публикации — существующий FTPS workflow. Локального файла с учётными данными панели или REG.RU API аудит не обнаружил в проекте и проверенных каталогах конфигурации.

До изменения панели сохранить текущие значения параметров/конфигурацию домена. При откате вернуть именно эти настройки отдельно: git revert не отменяет изменения панели. Официальные инструкции: [редирект через панель REG.RU](https://help.reg.ru/support/hosting/redirekty/redirekt-cherez-panel-upravleniya), [настройки сайта в ispmanager](https://www.ispmanager.ru/docs/ispmanager/rabota-s-saytom). Не переключать обработчик PHP или весь веб-сервер ради одного редиректа.
